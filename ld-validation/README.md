# ld-validation

Core HLA linkage disequilibrium (LD) detection library. This module has no CLI of its
own — see [`ld-tools`](../ld-tools) for the command-line entry points, or
[`ld-service`](../ld-service) for the REST wrapper. `ld-validation` is what actually does
the work: parsing GL Strings, matching candidate haplotypes against reference frequency
data, and reporting findings.

## Entry points

- **`org.dash.valid.LinkageDisequilibriumAnalyzer`** — batch driver. Reads one or more
  GL String files, runs detection over every genotype, and writes the report set
  (`summary.xml`, `linkages.log`, `haplotypePairs.log`, `detectedFindings.csv`, etc.) via
  the writer classes in `org.dash.valid.report`. This is what `ld-tools`'
  `analyze-gl-strings` CLI actually calls.
- **`org.dash.valid.HLALinkageDisequilibrium`** — the detection algorithm itself.
  `hasLinkageDisequilibrium(...)` takes a parsed genotype and returns a `Sample` carrying
  the detected linkages. Two overloads: one that enumerates all possible haplotypes from
  an (possibly ambiguous) unphased genotype, and one (`enrichHaplotype()`) that annotates
  already-known/phased haplotypes instead.

## Package layout

| Package | Purpose |
|---|---|
| `org.dash.valid` | Core model (`Locus`, `Linkages`, `DisequilibriumElement`) and the detection algorithm itself |
| `org.dash.valid.gl` | GL String parsing (`GLStringUtilities`) and the genotype-list abstraction (`LinkageDisequilibriumGenotypeList`) |
| `org.dash.valid.gl.haplo` | Haplotype and haplotype-pair representations, including the `equals()`/`hashCode()` contracts the tie-break logic depends on being correct |
| `org.dash.valid.freq` | Reference frequency data loading — NMDP haplotype frequency files (legacy per-locus-column `.xls`/`.xlsx` layout and the newer combined-haplotype layout), streamed via `StreamingXlsxRows` rather than loaded as a full DOM |
| `org.dash.valid.ars` | Antigen Recognition Site (ARS)/G-group ambiguity data (`hla_ambigs.xml`), used for allele-level matching that isn't exact-string |
| `org.dash.valid.cwd` | Common (and Common Intermediate) Well-Documented allele checking against IMGT/HLA reference data |
| `org.dash.valid.wmda` | WMDA serology-to-molecular-typing translation table loading |
| `org.dash.valid.report` | Findings model and the writer classes that produce each output file/log |
| `org.dash.valid.race`, `org.dash.valid.base`, `org.dash.valid.handler` | Supporting types (per-race frequency/rank data, base disequilibrium-element implementations, common-well-documented file handling) |

## Reference data

Both the IMGT/HLA reference XML (`hla.xml.zip`, `hla_ambigs.xml.zip`) and the NMDP
frequency reference files are pulled from external sources at runtime, controlled by a
handful of system properties — `org.dash.frequencies`, `org.dash.hladb`, `org.dash.ars`,
`org.dash.linkages` — documented under "Properties" in the [root README](../README.md). The
bundled 2007 NMDP dataset (`frequencies/nmdp-2007/*.xls`) is legacy OLE2 format, not
OOXML; loaders that read frequency files detect the actual container format via POI's
`FileMagic` rather than assuming from the file extension, since the two formats need
different readers.

## Tests

`src/test/resources` has several real (or synthetic-but-realistic) GL String files used
across the test suite — `contrivedExamples.txt`, `fullyQualifiedExample.txt`,
`shorthandExamples.txt`, `strictExample.txt`, and `syntheticExamples.txt` (generated by
`ld-tools`' `synthetic-gl-string-generator`; see `syntheticExamples.README.txt` for
provenance and regeneration instructions — it deliberately avoids real, identifiable
genotypes while still producing haplotypes findable in the bundled reference frequency
data).

Run the module's tests from the repo root: `mvn -pl ld-validation -am test`. Some tests
depend on which HLADB reference snapshot resolves at test time — see the `hladb` Maven
property and `-Dorg.dash.hladb` in the root README if a test's expected allele/G-group
counts look off after an IMGT/HLA release.

Coverage reporting (not gated) runs via JaCoCo as part of `mvn verify`; the HTML report
lands in `target/site/jacoco` and is archived as a CircleCI build artifact.
