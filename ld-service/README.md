# ld-service

REST wrapper around [`ld-validation`](../ld-validation)'s detection library, built on
Spring Boot 3 / Jakarta. The API surface is spec-first: `hlahapv-swagger-spec.yaml`
defines the contract, `openapi-generator-maven-plugin` generates the API interface and
model classes into `target/generated-sources` at build time, and
`GenotypesApiController` implements the generated interface.

## API

All endpoints return the same detected-linkage findings `ld-tools`' `analyze-gl-strings`
would produce for the same input, as JSON instead of the file-based report set (each
`SampleData` includes `hasAnomalies`/`warnings` plus a report string per `*.log`/`.csv` file
the CLI writes, generated by the same formatter classes):

- `POST /genotypes` (operation `submitGenotypes`): a JSON/XML body of pre-parsed
  `{id, glString}` pairs. Synchronous — returns the result directly.
- `POST /genotypes/file` (operation `submitGenotypesFile`, `multipart/form-data`): the same
  tab-delimited `id<TAB>glString`-per-line batch file format the CLI reads. **Asynchronous** —
  returns `202` with a `jobId` immediately; poll `GET /genotypes/jobs/{jobId}` for progress
  and the eventual result (see below).

Both accept optional `hladbVersion`/`frequencySet` fields to select the IMGT/HLA reference
database version and frequency set for the request, mirroring the CLI's `-v`/`-f` flags —
both genuinely apply per request. `POST /genotypes/file` additionally accepts
`frequencyFiles`/`allelesFile` uploads (the CLI's `-q`/`-l`): your own frequency reference
data, in the "standard format" `ld-tools`' `normalize-frequency-file` produces, from NMDP or
any other source — this is the actual point of letting an end user bring their own
frequencies rather than being limited to the handful of bundled named sets.

Requests are serialized (one analysis at a time): the underlying detection engine's
hladb/frequency-set selection is process-wide state, not threaded through per call, so this
is a deliberate, honest simplification for what's scoped as a personal/local tool, not a
general concurrent-request service.

### Why `/genotypes/file` is async

Measured against real converted NMDP frequency data (not a guess): parsing a single ~90MB
standard-format frequency file can take 8+ minutes on its own, before any genotype analysis
even starts, and this project's own larger converted datasets run 700MB–1GB+. A synchronous
request would sit well past any reasonable HTTP timeout with zero feedback — the CLI's own
"Processing gl string N of M" console logging never reached an HTTP caller at all. So instead:

1. `POST /genotypes/file` does a **cheap, synchronous sanity check** on any `frequencyFiles`
   upload (just the first few lines) — an obviously-wrong file still gets an immediate `400`.
2. It then hands the actual work (config + parse + analyze) to a single background worker
   thread and returns `202` with `{jobId}` right away.
3. `GET /genotypes/jobs/{jobId}` returns `{phase, processed, total, percent, result, error}`.
   `phase` is `QUEUED` → `LOADING_REFERENCE_DATA` (no percent — the parsing loop itself has no
   progress signal, so this is intentionally coarse) → `ANALYZING_GENOTYPES` (percent is
   meaningful here, reusing the CLI's own per-genotype counter via a `ProgressListener` hook
   added to `LinkageDisequilibriumAnalyzer`) → `DONE` (`result` populated) or `FAILED`
   (`error` populated — e.g. a file that passed the cheap upfront check but turned out
   malformed further in; that's a real, deliberate tradeoff of validating cheaply upfront
   rather than fully parsing before ever responding).

One worker thread, not a pool: this mirrors the CLI's own single-process model and preserves
the one-analysis-at-a-time invariant the hladb/frequency-set configuration already depends on
(see above) — a second concurrent job would risk racing that same process-wide state. Jobs
are tracked in memory only (a restart loses them) and evicted an hour after completion; none
of this is meant to survive as durable state, consistent with the personal/local-tool scope.

Interactive docs (springdoc-openapi) are served once the app is running:

- Swagger UI: `http://localhost:8080/swagger-ui/index.html`
- OpenAPI JSON: `http://localhost:8080/v3/api-docs`

`GET /actuator/info` reports the running build's version (`{"build":{"name":"ld-service",
"version":"1.0.0",...}}`) -- the browser UI's footer reads this to show its own version, the
same idea as the CLI tools' `-h`/`-a` version display.

## Browser UI

Once the app is running, open **`http://localhost:8080/`** for a browser UI covering the
same `analyze-gl-strings` workflow as the CLI and the `/genotypes/file` API above — it's
served as a static resource (`src/main/resources/static`) by this same Spring Boot app, no
separate setup. It supports:

- Pasting GL strings directly, or uploading a batch file — either way submits through the
  same async job API described above, so even a single pasted genotype gets progress
  tracking rather than a blocking request
- Selecting `hladbVersion`/`frequencySet`, or uploading your own `frequencyFiles`/`allelesFile`
- Live progress while the job runs (an indeterminate bar while reference data loads, a real
  percentage during genotype analysis)
- Results per sample: an anomaly/clean badge, warnings, haplotype-pair frequency tables, and
  the same four report texts the CLI writes to `*.log`/`.csv` files, each shown collapsed
- A "Download reports" button that assembles those report texts into one file

v1 covers `analyze-gl-strings` only — `normalize-frequency-file` and
`synthetic-gl-string-generator` remain CLI-only for now.

## Running it

Two ways: with Docker (nothing else to install) or directly with Java and Maven. Either way the
service ends up at <http://localhost:8080/> (browser UI) with the API docs at
<http://localhost:8080/swagger-ui/index.html>.

### Option A — Docker (easiest)

**You need:** [Docker Desktop](https://www.docker.com/products/docker-desktop/) (or any Docker
engine with the `docker compose` command), installed **and running**. No Java or Maven.

**Quickest — no clone, no build.** Each release is published as a ready-made image
(`linux/amd64` and `linux/arm64`, so Apple Silicon works natively) at
`ghcr.io/nmdp-bioinformatics/ld-service`, starting with the first release after 1.0.0:

```
docker run --rm -p 127.0.0.1:8080:8080 ghcr.io/nmdp-bioinformatics/ld-service:latest
```

Then open <http://localhost:8080/>; `Ctrl+C` stops (and removes) it. This version doesn't keep
the downloaded HLA reference data between runs — use the compose route below for that.

**With compose (keeps the reference data, easy to start/stop).** Needs this repository cloned.
`docker compose up` pulls the published image; if it can't (for example no release including it
exists yet), it builds the same image from your checkout instead, so the steps below work either
way.

1. Open a terminal and go to this directory (`ld-service`, inside the cloned repo):

   ```
   cd ImmunogeneticDataTools/ld-service
   ```

2. Start it:

   ```
   docker compose up
   ```

   If it has to build from source, the first run downloads base images and compiles the
   project, which takes several minutes (add `--build` to force a rebuild); pulling the published
   image is much quicker. The terminal then stays attached and prints the
   service's log. It is ready when you see a line like `Started HLAHapVServiceApplication`
   (about 30–60 seconds after the build finishes).

3. Open <http://localhost:8080/> in your browser.

4. To stop it, press `Ctrl+C` in that terminal, then optionally clean up with
   `docker compose down`.

Everyday use after that:

| I want to… | Run (from the `ld-service` directory) |
|---|---|
| Start it again | `docker compose up` |
| Start it in the background | `docker compose up -d` (then `docker compose logs -f` to watch, `docker compose down` to stop) |
| Update to the newest published release | `docker compose pull`, then `docker compose up` (a cached image is reused as-is) |
| Build from my checkout, e.g. after changing code | `docker compose up --build` |
| Check whether it's healthy | `docker compose ps` — the status column shows `healthy` once it's ready |
| Give it more memory for a big frequency upload | `JAVA_OPTS=-Xmx6g docker compose up` (and see "Heap size" below) |
| Start completely fresh (also forgets the downloaded reference data) | `docker compose down -v` |

Things worth knowing:

- **It only listens on your own machine** (`127.0.0.1`). The service has no login and accepts
  uncapped uploads, so it is deliberately not reachable from other computers on your network. To
  change that on purpose, edit the `ports` entry in `docker-compose.yml` to `"8080:8080"`.
- **It needs internet access on first use** to download the HLA reference data; that download is
  cached in a Docker volume, so restarts don't repeat it.
- **Docker Desktop's memory limit applies.** Its default is a couple of GB, which is fine for the
  bundled reference data but too small for large frequency-file uploads. Raise it under Docker
  Desktop → Settings → Resources.
- **Troubleshooting:** `Cannot connect to the Docker daemon` means Docker Desktop isn't running —
  start it and retry. `port is already allocated` means something else is using port 8080 — stop
  it, or change the left-hand `8080` in the `ports` entry. A container that never turns `healthy`:
  check `docker compose logs`.

Without compose, from the **repo root**: `docker build -f ld-service/Dockerfile -t ld-service:local .`
then `docker run -p 127.0.0.1:8080:8080 ld-service:local`.

### Option B — Java and Maven

**You need:** Java 25 and Maven (see the [root README](../README.md) for install notes). From the
**repo root**:

```
mvn -pl ld-service -am package
java -Xmx6g -jar ld-service/target/ld-service-1.0.0.jar
```

(`-Xmx6g` is the maximum memory the service may use — see "Heap size" below. Note that a plain
`java` command does not read a `JAVA_OPTS` environment variable; only the Docker setup does.)
Stop it with `Ctrl+C`.

### Heap size

A `frequencyFiles` upload is parsed fully into memory (the same
`HLAFrequenciesLoader.loadStandardReferenceData` path the CLI's `-q` uses) and held there
for the life of the process, at roughly 4–6x the file size — the NMDP nine-locus release
(~1 GB) needs `-Xmx4g` minimum, `-Xmx6g` comfortably, and a too-small heap fails with an
`OutOfMemoryError` that takes down every in-flight job. The container defaults to
`-XX:MaxRAMPercentage=75.0` (75% of the container's memory), overridable with `JAVA_OPTS` —
for example `JAVA_OPTS=-Xmx6g docker compose up`. Docker Desktop's VM defaults to only a couple
of GB, so raise it under Settings → Resources before uploading large frequency files. A bare
`java -jar` run gets only the JVM default (~25% of RAM), so pass `-Xmx` explicitly (e.g.
`java -Xmx6g -jar …`) if you'll upload large frequency files. See the
[root README](../README.md)'s "Memory / heap sizing" note.

## `ld-client`

The `ld-client` subdirectory is a separate, fully auto-generated Maven module — an
OpenAPI/Swagger Java client for this same `hlahapv-swagger-spec.yaml` contract, generated
by `swagger-codegen-maven-plugin`. Its own `README.md` is generator boilerplate, not
hand-maintained; regenerate rather than hand-edit it if the spec changes.
